### Add or Update Component

There is one Eeschema command and one review-dialog class. The action selects its mode from the current schematic selection: exactly one editable symbol opens update mode; an empty selection opens add mode. Both modes now share the same window dimensions, catalogue-photo card, supplier metadata, match table, proposed-field review and footer. Only the KiCad symbol and placement inputs differ by context. The live examples use resistor records for deterministic supplier data; non-passive behavior is covered by the unit-test suite described below.

## What is exercised

The visual capture runs the production application windows, not separately drawn mockups. It forces the light palette, reapplies the dark palette to each live root, and captures both states from the same widgets; this checks that theme changes update ttk and classic Tk controls without rebuilding the window.

| Workflow | Live GUI / IPC evidence |
| --- | --- |
| Component Overview | Captures unfiltered, filtered and selected-row states. Verifies live JLCPCB detail source, product image, MPN alternatives and the completed cost/stock summary. |
| Component Properties | Opens the focused properties window from a selected linked Eeschema symbol and captures its loaded catalogue view. |
| Properties controls | Calls Select in schematic and Select same part on sheet; verifies the Eeschema selection; copies the LCSC ID and verifies the clipboard; invokes LCSC search, supplier product, datasheet and MPN-result actions and checks that each opens an HTTPS URL. |
| Add or Update Component — update mode | Selects a generic resistor in Eeschema, drives the actual LCSC lookup/review window, verifies the shared match list and catalogue preview, waits for the asynchronous supplier image when present, captures the proposal and native confirmation, applies the reviewed update and reads the resulting fields back through IPC. |
| Add or Update Component — add mode | Clears the Eeschema selection, drives the same lookup/review layout with X/Y placement values, verifies the match list and catalogue preview, waits for the supplier image when present, captures the proposal and native confirmation, generates and places the project-local symbol, then verifies its reference, library ID and linked metadata through IPC. |
| Theme pairs | Captures the overview, properties and both Add or Update Component modes in both light and dark palettes, reusing each live widget tree. |
| Native symbol examples | Exports the stock resistor/capacitor symbols, and the live fixture also exports the generated project-local passive symbol, with KiCad CLI. |

The live GUI capture verifies both selection contexts of the unified action using resistor examples: update mode requires a fresh direct response for LCSC C60489 and verifies its 10 kΩ / 0402 interpretation; add mode independently fetches LCSC C105637 and verifies its 1 kΩ / 0402 interpretation. These examples demonstrate the shared dialog and its context-dependent controls; they do not define the supported component scope. Unit tests additionally cover inductor/LED classification, arbitrary selected-symbol metadata updates, multi-pin IC symbol copying and manual KiCad symbol selection. The GUI capture does not yet exercise every non-passive family or the manual symbol-entry interaction. Both mode-specific screenshots fail closed rather than silently falling back to cached data. The proposal/result screenshots document those controlled examples; the actual supplier facts are those returned at capture time.

## Capture design

The demo schematic is populated through the live KiCad IPC API with controlled example references, values, LCSC links and MPN fields. The first resistor is initially a placeholder; the fixture then exercises the same draft builder and IPC write-back used by the general update mode.

For generated-library coverage, the fixture seeds a project-local `JLCPCB_Generated` table entry and a `C60489` resistor *before* Eeschema starts. This lets the add mode fetch a second part (`C105637`), extend the already-loaded library, and place the new linked symbol without hitting the first-use table-registration limitation. The test checks the generated library's native fields, hidden custom metadata, stock two-pin topology, project table entry, schematic library ID and KiCad CLI export. Separately, a unit test covers the first-use reload failure and verifies that the error explains the saved table row and the required close/reopen/retry workflow.

The properties-control capture checks:

- Selecting the currently highlighted symbol in Eeschema.
- Selecting all occurrences of that same part on the current sheet.
- Copying the selected part ID to the clipboard.
- Opening the LCSC search, product page, datasheet and an MPN comparison result; each destination must be HTTPS.

The visual fixture exercises these navigation controls on the root sheet. Hierarchical sheet discovery and `FocusOnItems` sheet-path selection have unit-test coverage, but this capture does not claim to visually validate plugin-manager discovery or navigation on a populated child sheet in a multi-sheet GUI project. Those remain separate release-validation items.

## Supplier-data provenance

The schematic's reference/value/LCSC/MPN fields are test inputs. Product descriptions, manufacturer, package, attributes, stock, price ladder, MPN search rows and the product photo are fetched from JLCPCB during the visual job. The image is downloaded from a supplier HTTPS URL; it is not generated artwork.

The workflow fails closed if it cannot obtain fresh direct JLCPCB detail data for the selected fixture, an image, stock/price, purchasable MPN-search results or the expected exact-MPN listing. The `manifest.json` records the source commit, KiCad CLI renderer version, asset inventory and SHA-256 hashes. Catalogue values and product availability are snapshots, not a binding quote or stock reservation.

The JLCPCB detail and MPN search requests use undocumented supplier website endpoints, not an official public components API. Successful capture verifies only the response shape available at that run; it does not guarantee that the supplier endpoints remain stable.

## CI generation and publication

The `visual-docs` CI job installs KiCad nightly, the matching `kicad-python` wheels, Tk, Pillow, Xvfb and `xdotool`. It launches Eeschema with an isolated profile, enables the IPC server, reconnects through the real socket and drives the schematic and production UI.

Pull-request runs upload the generated directory as the `kicad-jlcpcb-visual-docs` workflow artifact. Successful pushes to `main` publish the hash-verified assets to the separate `docs/previews` branch. The README and this page embed those published assets. The publishing step records the source SHA and workflow run and verifies the remote branch head after pushing.

## Reproduce locally

On Ubuntu, install the same classes of system dependencies used by CI, then run:

```bash
sudo apt-get install kicad-nightly kicad-nightly-symbols python3.12-venv python3-tk python3-pil python3-pil.imagetk xvfb xauth xdotool
python3.12 -m venv --system-site-packages .venv-visual
.venv-visual/bin/pip install -r plugin/kicad-jlcpcb-interface/requirements.txt
xvfb-run -a -s "-screen 0 1920x1500x24" \
  .venv-visual/bin/python tests/capture_visual_docs.py --output-dir artifacts/visual-docs
```

The script also accepts `KICAD_CLI` and `KICAD_SYMBOL_DIR` to select explicit KiCad CLI and symbol-library paths. Generated files are disposable outputs; change the capture fixture or generator and regenerate them instead of editing preview images by hand.

## Evidence boundary

The screenshots demonstrate the production Tk windows and real Eeschema IPC actions exercised by the visual fixture. They do not establish universal support for all component families, supplier search equivalence, plugin-manager registration on every KiCad build, or correct electrical/PCB suitability of a generated part. Always verify symbol type, footprint, pin topology, catalogue attributes and current supplier terms against the actual design before manufacturing.
